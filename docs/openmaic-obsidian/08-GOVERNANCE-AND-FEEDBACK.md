# 文档治理、专家复审与反馈机制

> 状态：`Proposed`  
> 目标：让 PRD、架构、实现、测试与真实学习结果持续一致，而不是在开工后各自过期

## 1. 治理原则

1. **证据优先于进度叙述**：完成必须对应可复现测试、真实样本或运行指标。
2. **先改决策文档，再改不可逆实现**：涉及数据权威、协议、安全、删除、供应商或核心旅程的变化，先完成评审。
3. **产品与架构双向约束**：PRD 不能要求架构无法安全承载的行为；架构也不能擅自削弱学习目标。
4. **保留历史原因**：重要决策用 ADR 和变更记录标记 `Superseded`，不直接抹掉。
5. **角色可由同一人承担，检查视角必须分离**：个人项目也要分别做产品、架构、开发、安全和学习质量检查。
6. **反馈必须落到动作**：每个信号都要有阈值、负责人、截止点和对应文档。

## 2. 文档体系与权威顺序

```text
愿景与原始方向
  ↓ 约束
PRD（用户价值、范围、验收）
  ↔ 架构文档（边界、质量属性、演进）
      ↓
数据/API/同步规范 + ADR
      ↓
里程碑、Issue、实现与迁移
      ↓
测试/发布证据 + 真实学习指标
      └──────────反馈回 PRD、架构和路线图
```

| 文档 | 权威内容 | 不应承载 |
|---|---|---|
| `01-VISION-AND-SCOPE` | 原始方向、北极星、边界、反目标 | 具体表结构 |
| `02-RESEARCH...` | 外部证据、时效性假设、竞品教训 | 已接受产品决策 |
| `03-IMPLEMENTATION-FLOW` | 阶段顺序、Gate、探针 | 字段级 API |
| `04-PRD` | 用户旅程、需求、指标、验收 | 平台 SDK 细节 |
| `05-ARCHITECTURE` | 系统边界、权威、质量属性、演进 | 逐项用户文案 |
| `06-DATA-API-SYNC-SPEC` | 领域 Schema、状态机、接口与同步 | 产品优先级 |
| `07-RISK-TEST-ACCEPTANCE` | 风险、测试、发布证据、Go/No-Go | 未评审的新需求 |
| `08-GOVERNANCE...` | 决策、反馈与文档更新方法 | 具体实现代码 |
| `09-DELIVERY-ROADMAP` | 依赖、批次、交付顺序、退出条件 | 长期不变的产品方向 |

发生冲突时，先回到 [总索引的证据优先级](./00-INDEX.md#7-证据优先级)，再提交显式变更，不靠口头解释绕过。

## 3. 需求—实现—证据追踪链

所有 P0 工作项必须能沿以下链路双向追踪：

```text
Objective / JTBD
→ PRD Requirement ID
→ Architecture component + ADR
→ API/Schema contract
→ Milestone + Issue/PR
→ Test case
→ Release evidence
→ Product/learning metric
→ 保留、修正或删除决策
```

建议建立 `traceability.csv` 或项目面板，字段至少包含：

| 字段 | 示例 |
|---|---|
| Requirement | `SRC-003` |
| User outcome | 只上传本次明确选择的笔记 |
| Architecture | SourcePackager / BlobPort / SourceRepository |
| Contract | `source-bundle/1`、`POST .../initiate` |
| Risks | R-04、R-05、R-06 |
| Tests | `contract-source-bundle`、E2E-01、security-upload |
| Evidence | Gate 2/4 evidence link |
| Metric | 选源撤销率、越界上传数、引用覆盖率 |
| Status | Proposed/In delivery/Validated |

没有 Requirement ID 的代码改动只能是修复、重构或基础设施，并且必须说明它保护的质量属性。

## 4. 角色与决策权

| 决策 | Product Owner（用户） | 产品经理视角 | 架构师视角 | 开发负责人视角 | 安全/质量视角 |
|---|---|---|---|---|---|
| 愿景、P0 范围、取舍 | A | R | C | C | C |
| 学习闭环与指标 | A | R | C | C | C |
| 数据权威、协议、迁移 | C | C | A/R | R | C |
| 实现计划与估算 | C | C | C | A/R | C |
| 隐私、安全、删除红线 | C | C | R | R | A |
| Gate 关闭 | A | R | R | R | R |
| 正式发布/回退 | A | C | C | R | R |

`A` 为最终负责，`R` 为执行评审，`C` 为必须征询。个人开发时可以由用户与 AI 协作承担多个角色，但每个 Gate 必须按各列分别回答问题，不能用一次自评替代全部视角。

## 5. 本轮专家复审记录

本轮方案经过四个相互独立的检查视角，结论已合并进本文档组。

### 5.1 产品经理检查

发现：如果目标写成“课程生成 + Obsidian 同步”，产品会优化内容数量，而不是项目推进。

采纳：

- 核心任务改为“从真实项目卡点，到可验证交付物，再到可复用知识”。
- 北极星指标使用“每周有效项目学习闭环数”。
- 区分知识状态、能力状态、记忆状态。
- 把主动尝试、真实 Evidence、迁移任务和复习纳入闭环完成条件。

### 5.2 架构师检查

发现：最容易导致大重构的是把 Vault 当云数据库、把插件嵌进 Web 代码、把长任务绑在函数生命周期，以及把掌握度存成不可解释分数。

采纳：

- Vault 权威 + 云端不可变快照 + 领域级同步。
- 独立插件、版本化协议和可替换基础设施端口。
- 持久 Workflow + 业务 Job + checkpoint。
- LearningEvent 为事实，Mastery/Review 为可重建投影。
- P0 受控写回，长期才评估更丰富的语义级双向同步。

### 5.3 开发负责人检查

发现：当前 OpenMAIC 可复用课堂 DSL、导入导出和 Runtime 契约，但当前本地文件持久化、内存状态、`after()`、请求体限制和浏览器本地学习记录不能直接支撑正式集成。

采纳：

- 不让插件直接调用现有课堂生成 route。
- 先做 API/Schema、Postgres、私有 Blob、持久 Job、Outbox/Inbox。
- 设置五个高风险探针，再进入完整 P0。
- 依赖升级和现有功能回归成为 Gate 0。

### 5.4 类似项目与学习研究检查

发现：知识检索、笔记内聊天、闪卡调度、项目式学习和 AI 导师各自已有成熟实践，但很少有产品同时打通“来源—教学—真实证据—受控回写—迁移复习”。

采纳：

- 借鉴 Khoj/Copilot/Smart Connections 的来源与引用透明度；
- 借鉴 Obsidian_to_Anki 的稳定映射和增量更新思路；
- 借鉴 Anki/FSRS 的复习事件与可配置负担，但不在 P0 盲目启用复杂算法；
- 借鉴 OATutor/Khanmigo 的分级提示和不替用户完成任务；
- 借鉴 PBLWorks 的真实问题、持续探究、反馈修订和公开成果质量标准；
- 把来源 revision、Evidence、rubric、迁移任务和答案泄漏率补进需求。

### 5.5 争议与最终裁决

| 争议 | 候选 | 裁决 | 重新评估条件 |
|---|---|---|---|
| 同步范围 | 全 Vault 双向 / 领域级同步 | P0 领域级同步 | 受管内容冲突率低且用户确有跨端编辑需求 |
| 默认回写 | 改原笔记 / 新建受管记录 | 新建受管记录 | 至少 100 次无静默冲突写回后评估受管区块更新 |
| 认证 | 复用 ACCESS_CODE / 配对 token / 完整 OIDC | P0 配对 token，长期 OIDC | 多用户或第三方客户端进入计划 |
| 复习算法 | 立即 FSRS / 固定规则 | P0 固定、保留完整事件 | 复习样本足够、参数可验证且队列负担可控 |
| 任务平台 | `after()` / Queue / Workflow | P0 持久 Workflow | 吞吐或成本数据证明需要事件队列拆分 |

## 6. 反馈节奏

### 6.1 每个工作日：实现反馈（10–15 分钟）

- 今天关闭了哪个 Requirement/Test？
- 是否出现新假设、数据形状或异常路径？
- 是否修改了协议、安全边界或用户可见行为？
- 证据链接在哪里？

若答案涉及一级决策，暂停合并并进入变更流程。

### 6.2 每周：产品与学习闭环复盘（30–45 分钟）

查看：

- 有效闭环数、从 Blocker 到 Evidence 的中位时间；
- 主动尝试率、答案泄漏率、Evidence 通过率、迁移表现；
- 回写接受/编辑/拒绝/冲突率；
- 复习到期、完成、跳过和积压；
- 最大失败案例和本周真实节省/增加的时间。

输出只能是：保持、修改实验、修复质量、删除低价值功能、升级决策。不能只输出“继续观察”而没有下次判定阈值。

### 6.3 每个里程碑：Gate 复审

按产品、架构、开发、安全、学习质量五个视角逐项签核 [验收矩阵](./07-RISK-TEST-ACCEPTANCE.md#10-gate-验收矩阵)。任何视角可基于证据触发 No-Go。

### 6.4 每月：平台与上游核对

- Vercel Functions、Blob、Workflow/Queues 的限制和价格；
- Obsidian API、移动端兼容、插件发布规范和密钥 API；
- React/Next/OpenMAIC 官方发布与安全公告；
- 模型供应商数据保留、API Schema 和成本；
- upstream OpenMAIC 与本分支的差异。

时效性资料超过 30 天且即将指导实现时必须重新核对官方来源。

## 7. 变更分类与流程

### 7.1 变更等级

| 等级 | 示例 | 流程 |
|---|---|---|
| C0 编辑性 | 错字、链接、无语义格式 | 直接修改，记录日期 |
| C1 兼容性 | 新增可选字段、UI 文案、内部重构 | PR + 测试 + 文档同步 |
| C2 行为性 | 验收变化、新状态、新命令、保留期变化 | 变更提案 + 产品/架构/安全复审 |
| C3 方向性 | 权威来源、认证、同步模型、删除策略、北极星变化 | Product Owner 批准 + ADR + 迁移/回退 + 全套 Gate 影响评估 |

### 7.2 变更提案模板

```markdown
# Change: <标题>
- 等级：C1/C2/C3
- 触发证据：指标、失败案例、官方变化或用户需求
- 当前行为与问题：
- 建议行为：
- 对原始方向的影响：保持/增强/可能偏离
- PRD Requirement：
- 架构/API/数据影响：
- 隐私、安全、成本与迁移：
- 被否决的替代方案：
- 测试与回退：
- 决策人、日期、复审日期：
```

顺序：提交提案 → 影响分析 → 更新 PRD/架构草案 → 评审 → 写 ADR/迁移 → 实现 → 验证 → 将文档状态改为 Validated。紧急安全修复可以先阻断风险，但必须在 24 小时内补齐记录。

## 8. ADR 与架构适应性检查

以下决策必须有独立 ADR：

- 数据权威与 SourceBundle 快照；
- 插件边界与版本化协议；
- Job/Workflow 持久化；
- 认证与 device/vault 绑定；
- LearningEvent 与 Mastery 投影；
- Writeback allowlist 和冲突策略；
- 数据保留、删除与导出；
- 基础设施供应商选择和迁移边界。

每次 CI/发布应运行架构适应性检查：

- 生产代码不得向 `process.cwd()/data` 写业务状态；
- domain/application 不得直接 import Vercel/数据库/Obsidian SDK；
- 所有 `/api/v1` 副作用路由要求幂等键；
- 所有 owner 数据查询必须具备 owner scope；
- 未知 writeback operation 默认拒绝；
- LearningEvent 表不允许 UPDATE/DELETE 的普通业务路径；
- 私密正文不得进入日志 Schema；
- 每个 PRD P0 ID 至少关联一个测试。

## 9. 指标触发器与强制动作

| 信号 | 阈值 | 强制动作 | 更新文档 |
|---|---:|---|---|
| Writeback 冲突率 | 连续 20 次中 > 10% | 暂停扩展写回，检查 hash/用户流程 | PRD、架构、风险 |
| 引用可打开率 | < 95% | 阻断课堂质量发布，修复锚点恢复 | PRD、协议、测试 |
| 答案过早展示率 | > 10% | 调整导师策略和 UI；复测固定集 | PRD、评测 |
| Evidence 产生率 | < 50% | 缩短冲刺、重写任务与验收 | 愿景假设、PRD |
| 迁移表现无改善 | 连续 10 个闭环 | 暂停功能扩张，复审教学设计 | PRD、研究、路线图 |
| 复习积压 | 到期 7 天仍未完成 > 30% | 降低生成量、允许暂停/合并 | PRD、调度规范 |
| Job 重试放大 | 单 Job 平均模型步骤 > 1.2 倍设计值 | 检查幂等和 checkpoint，启用成本熔断 | 架构、风险 |
| 任意静默覆盖/越权 | > 0 | 立即停用写回/相关 token，启动事件流程 | 风险、ADR、事故记录 |

阈值在个人样本较少时作为诊断触发器，不伪装成统计结论。

## 10. 事故、回退与复盘

严重事件包括：未授权外发、跨用户访问、Vault 静默覆盖、不可恢复数据丢失、重复高额费用和删除失效。

处理顺序：

1. 停止相关能力：撤销 token、关闭功能旗标、暂停 Worker/Workflow；
2. 保存不含正文的审计与关联 ID，保护用户原始数据；
3. 界定范围、时间和可恢复路径；
4. 回退应用/插件或发布向前修复；
5. 验证修复与数据完整性；
6. 形成无责复盘：根因、为何控制失效、修复、测试、文档与负责人；
7. 更新风险分数、ADR、验收项和用户可见已知限制。

未经用户确认不得用“自动修复”覆盖冲突文件。

## 11. 文档维护规则

每份文档头部维护：状态、版本、最后复审日期、适用版本、负责人。每次里程碑发布：

- 同一 PR 更新代码、测试和相关文档；
- `CHANGELOG` 记录用户可见行为、协议和迁移；
- 过时内容标记 `Superseded by ...`，保留原因；
- Open Questions 每项有 owner、截止 Gate 和默认安全行为；
- 发布后 48 小时内填入真实结果并把已验证条目改为 `Validated`。

文档如果与运行行为冲突，先将对应能力标为不可信/未验证，再用测试确认真实行为，不能默认代码或文档任一方自动正确。

## 12. 当前下一次决策会

进入编码前，按顺序完成：

1. 用户确认 P0 范围、数据保留、附件范围和外部检索默认值；
2. 架构复审 `SourceBundle/Writeback/LearningEvent` 三个契约；
3. 开发复审五个高风险探针和依赖升级影响；
4. 安全复审配对、私有直传、日志与删除；
5. 将 Gate 1 条目设为 Accepted，并创建 [交付路线图](./09-DELIVERY-ROADMAP.md) 中的首批 Issue。

任何新想法先进入 Decision Log，不直接插入当前里程碑；除非它解决当前 Gate 的阻断风险。
