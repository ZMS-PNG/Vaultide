# 完整实现流程

> 状态：Proposed  
> 目的：把产品方向、研究结论、专家审查、架构和开发交付连接成可执行流程。  
> 原则：每个阶段都有输入、动作、产物、退出条件和回退路径；未通过阶段门，不扩大范围。

## 2. 总体交付策略

### 2.1 先做一个端到端纵切片

首个可用版本只证明一个高价值场景：

> 用户在真实项目中遇到一个具体问题，选择 1–10 篇 Obsidian 笔记，在一次 15–45 分钟学习冲刺内完成诊断、主动练习和真实项目任务，经验证后把错误、决策、证据和复习计划安全写回 Obsidian。

不先做全 Vault 索引、知识图谱、多人协作和自主 Agent。只有纵切片真实节省时间并改善延迟表现，才进入扩展。

### 2.2 代码组织策略

当前仓库是 OpenMAIC 上游快照。建议在用户自己的 GitHub 账户建立 fork/派生仓库，并保留 `upstream` 远端。首期不大规模搬迁目录：

```text
OpenMAIC 现有应用
├─ packages/@openmaic/learning-protocol   # 稳定跨端契约
├─ integrations/obsidian                  # 独立构建、独立发布的插件
├─ lib/learning                           # Web 领域用例与端口
├─ app/api/integrations/obsidian          # 配对、来源、任务、回写 API
└─ docs/openmaic-obsidian                 # 本文档组
```

插件与 Web 可以同仓开发，但必须能独立构建，并且只能通过版本化 HTTP/JSON 协议通信。这样既减少个人维护成本，又不形成源码级耦合。

### 2.3 五条并行工作线

| 工作线 | 范围 | 不能越界 |
|---|---|---|
| 产品与学习设计 | 项目模型、冲刺、量规、指标和实验 | 不用主观体验替代学习结果 |
| Obsidian 插件 | 选源、本地筛选、配对、上传、回写与复习入口 | 不持有模型密钥，不静默改笔记 |
| OpenMAIC Web | 项目入口、诊断、课堂、证据提交和结果展示 | 不成为原始知识事实源 |
| 云端基础 | 身份、Postgres、Private Blob、Workflow、审计 | 不把供应商 SDK渗入领域模型 |
| 质量与安全 | 契约、故障、注入、冲突、隐私和学习效果测试 | 不等到上线前才补安全 |

## 3. 阶段 0：基线冻结与可测性

### 目标

确认当前系统、部署和用户原始学习流程，避免开发后无法判断是否有效。

### 动作

1. 在用户自己的派生仓库记录 OpenMAIC 上游 commit、版本和许可证。
2. 保留当前 Vercel 部署作为只读演示基线；新功能在 Preview 环境开发。
3. 对照 React/Next 官方版本与安全公告升级当前依赖，并完成课堂生成、播放器、导入导出和 Runtime 回归。
4. 记录两周个人学习基线，每次项目卡点至少记录：
   - 问题出现时间；
   - 找到有效资料所需时间；
   - 学习和整理时间；
   - 独立完成任务时间；
   - 返工原因；
   - D1/D7 是否还能解释或应用。
5. 建一个专用的 Obsidian 开发 Vault，只放脱敏测试资料。
6. 建立最小隐私清单：允许外发的目录、绝不外发目录、默认保留期。
7. 为 P0 选一个真实、可在一周内完成的项目任务作为黄金案例。

### 产物

- `Baseline Study Log`；
- 10–20 个脱敏来源笔记；
- 一个黄金项目场景及验收量规；
- 上游同步和分支策略；
- 个人数据分类表。

### Gate 0：是否可以开始设计冻结

- 有至少 5 次真实项目卡点记录；
- 黄金场景存在客观交付物和验收条件；
- 测试 Vault 与主 Vault 完全分离；
- 当前部署和代码基线可回退；
- Web 依赖已升级到当时官方支持且覆盖已知安全公告的版本，现有核心功能回归通过。

## 4. 阶段 1：产品与协议冻结

### 目标

在编码前冻结 P0 用户旅程、跨端协议和数据所有权。

### 动作

1. 评审 [PRD](./04-PRD.md) 中 P0/P1/P2，删除无法服务核心闭环的需求。
2. 逐一确认 SourceBundle、LearningSprint、LearningEvent、ProjectEvidence、WritebackDraft、ReviewItem 的字段。
3. 冻结“原文默认只读、受管新建回写”的规则。
4. 冻结设备配对和令牌作用域；禁止复用站点 ACCESS_CODE。
5. 冻结 P0 固定复习策略 D1/D7/D30；FSRS 仅保留数据兼容性。
6. 为每个 P0 需求写 Given/When/Then 验收用例。
7. 建立首批 ADR，并指定谁能改变已冻结决策。

### 产物

- PRD v1；
- 架构 v1；
- JSON Schema / TypeScript 协议草案；
- API 契约草案；
- ADR-001 至 ADR-005；
- 验收矩阵 v1。

### Gate 1：产品与协议冻结

所有问题必须能回答“是/否”：

- 用户是否总能知道本次选择了哪些来源？
- 每个学习冲刺是否绑定交付物和验收条件？
- 原始笔记是否在默认路径中保持 0 次自动修改？
- 每个重要结论是否能回到来源段落或标为推断？
- 每个远端写操作是否有幂等键？
- 每个高风险动作是否由确定性代码检查并经用户确认？
- 数据能否导出、删除，设备令牌能否撤销？
- P0 是否可以在不实现向量数据库和 FSRS 的情况下完成？

只要任一答案不明确，不能进入完整开发。

## 5. 阶段 2：高风险技术探针

### 目标

用最少代码验证最可能导致重构的边界，不做完整 UI。

### 探针 A：Obsidian 安全选源

1. 插件列出 Markdown 文件、标题、标签和链接元数据。
2. 用户选择 1–10 个文件。
3. 插件生成 SourceBundle：稳定 ID、路径、mtime、内容哈希、标题块和原文。
4. 文件在打包过程中变化时检测并中止。
5. Windows、macOS 与移动端至少完成 API 兼容性检查。

退出条件：不使用 Node 文件系统也能完成选源；未选文件字节数为 0。

### 探针 B：设备配对

1. Web 生成一次性、短时配对码。
2. 插件提交配对码和设备信息。
3. 服务端只返回作用域设备令牌，并保存令牌哈希。
4. 插件优先保存到 SecretStorage。
5. Web 可立即撤销，撤销后下一请求必须失败。

退出条件：不需要把 ACCESS_CODE 或 LLM Key 写入插件。

### 探针 C：大文件直传与隐私

1. API 签发一次性 Private Blob 上传授权。
2. 插件直接上传超过 4.5 MB 的测试 SourceBundle。
3. 服务端用哈希、大小、MIME 和 owner 校验并登记。
4. 超时、重复和中断重试不会创建多份逻辑对象。
5. 删除后元数据和对象都可验证清理。

退出条件：普通 Function 请求体不承载大文件；对象不可被公开 URL 读取。

### 探针 D：持久生成任务

1. 将最小“解析 → 诊断 → 生成一个场景 → 保存”拆成持久步骤。
2. 在步骤间模拟 Function 崩溃和重新部署。
3. 重试不重复计费、不重复写课堂、不重复发送回写。
4. Postgres 中能看到独立于 Workflow 控制台的业务状态。

退出条件：任务可恢复、可取消、可重试、可观察。

### 探针 E：冲突安全回写

1. 服务端产生结构化 WritebackDraft。
2. 插件展示即将创建或修改的 Markdown diff。
3. 在确认前人为修改目标文件。
4. 插件必须检测 baseHash 不一致并停止覆盖。
5. 重复点击确认只写入一次。

退出条件：并发修改不会丢失；写入可撤销或进入回收路径。

### Gate 2：技术可行性

五个探针必须全部通过。若持久任务或冲突回写失败，立即调整架构，不能靠 UI 遮盖。

## 6. 阶段 3：基础骨架

### 目标

建立可持续开发的协议、身份、存储和可观测性骨架。

### 实现顺序

1. `@openmaic/learning-protocol`
   - 领域 ID、版本、JSON Schema、校验器；
   - SourceBundle、Project、LearningSprint、LearningEvent、WritebackDraft；
   - 向后兼容测试和迁移注册表。
2. Postgres
   - owner/device、project、source snapshot、sprint、job、artifact、writeback、review 和 audit 表；
   - 迁移工具、约束、租户分区和幂等唯一索引。
3. 对象存储
   - Private Blob 适配器；
   - 不可变路径、内容哈希、保留期和删除作业。
4. 任务编排
   - `JobOrchestrator` 端口；
   - Vercel Workflow 适配器；
   - 每步重试分类、取消、补偿和心跳。
5. 身份
   - 单用户 owner、站点会话和设备令牌分离；
   - 令牌作用域、轮换、撤销和审计。
6. 观测
   - requestId、jobId、sprintId、deviceId 贯穿日志；
   - 模型调用成本、延迟、重试和错误分类；
   - 日志禁止原文、密钥和完整模型 Prompt。

### Gate 3：骨架完整性

- 协议契约测试在 Web 和插件两端运行；
- 数据库可从空库迁移并回滚一个测试版本；
- 同一幂等请求执行三次只产生一个逻辑结果；
- 删除用户数据能列出并清理所有派生对象；
- 无任何课堂或任务写入 `process.cwd()/data`。

## 7. 阶段 4：P0 纵切片

### 7.1 用户端完整路径

1. 在 Obsidian 安装插件并与 OpenMAIC 配对。
2. 创建 Project：目标、阶段、截止时间、交付物和验收标准。
3. 输入当前 Blocker 和期望的 15/30/45 分钟预算。
4. 插件根据路径、标题、标签、链接和关键词建议候选笔记。
5. 用户逐项确认；插件显示文件数、字节数、外发目的和保留期。
6. SourceBundle 上传后，Web 展示来源清单和版本。
7. 系统先生成 2–5 个诊断题；用户必须先作答。
8. 诊断结果形成最短学习计划，用户可删减或调整。
9. OpenMAIC 生成并执行必要场景：微讲解、回忆、Quiz、互动或 PBL。
10. 系统要求用户回到真实项目完成一个交付动作。
11. 用户提交 ProjectEvidence；优先运行自动检查，其次量规和 AI 辅助反馈。
12. 系统生成包含来源、错误、决策、证据、下一步和复习项的 WritebackDraft。
13. 插件显示预览，用户确认后在受管目录新建学习记录。
14. 系统创建 D1/D7/D30 复习任务，并在 Obsidian Dashboard 中显示。

### 7.2 P0 必须实现的最小界面

Obsidian：

- 连接状态和撤销；
- 项目/卡点表单；
- 来源选择与范围预览；
- 上传/任务状态；
- 回写差异与确认；
- 今日复习和打开课堂。

OpenMAIC Web：

- 项目上下文和来源面板；
- 诊断；
- 学习冲刺计划；
- 课堂运行；
- 证据提交与量规；
- 结果、来源、回写和复习计划。

### 7.3 场景选择规则

| 学习目标 | 首选场景 | 约束 |
|---|---|---|
| 建立概念模型 | slide + 无提示解释 | 讲解后必须让用户重建 |
| 辨析与决策 | 多智能体对比 + 用户最终判断 | Agent 观点必须引用来源，用户先给立场 |
| 程序/操作技能 | interactive/code + 真实项目动作 | 不用观看演示代替亲手执行 |
| 检查理解 | short-answer quiz | 首答不可看答案，反馈引用来源 |
| 综合应用 | PBL 微里程碑 | 有真实交付物、量规、批评与修订 |

### Gate 4：内部 Alpha

- 黄金场景从选源到回写完整成功 10 次；
- 至少覆盖一次网络中断、任务重试、文件冲突和设备撤销；
- 重要输出引用覆盖率 100%，无证据处明确标为推断；
- 原始来源自动修改 0 次；
- 重复提交不会重复建项目、课堂、事件或笔记；
- 一次完整冲刺的失败可以从明确步骤继续，不需全部重来。

## 8. 阶段 5：学习质量与自适应

### 目标

证明系统改善学习，而不是只让体验更丰富。

### 动作

1. 建立显式映射：LearningObjective → Activity → Attempt → Evidence。
2. 保存首答、提示次数、用时、来源、评分依据和是否独立完成。
3. 增加“下一题/下一任务独立完成率”，检测 AI 是否过早泄露答案。
4. 对开放式任务实行：确定性检查 > 人工量规 > AI 辅助评分。
5. 实施 D1/D7/D30 复习；记录无提示正确率和迁移表现。
6. 只允许用户确认的高价值知识进入复习队列。
7. 对难复习项提供拆分、重写、暂停和删除，而非无限重复。
8. 比较两种策略：
   - A：先讲解再测验；
   - B：先诊断/尝试再针对性讲解。

### Gate 5：学习价值

至少完成四周个人试用，并满足：

- ≥ 70% 冲刺产生项目证据；
- 相比基线，开始有效练习时间下降 ≥ 30%；
- D7 无提示表现有明确正向趋势；
- 总开销没有增加；
- 用户确认“下一任务能独立完成”的比例提升；
- 回写草稿接受率和未来复用率可测。

若不满足，暂停知识图谱、全量同步和 Agent 扩展，优先修正诊断、练习和证据环节。

## 9. 阶段 6：安全、可靠性与恢复

### 动作

1. 对来源笔记、附件、网页和模型输出执行不可信数据隔离。
2. 建提示注入测试集：直接、间接、隐藏链接、Markdown/HTML、代码注释和来源冲突。
3. 工具只能接收结构化参数；每个工具独立鉴权，模型不持有令牌。
4. 对写入、删除、外发和执行动作加入确认和审计。
5. 进行租户越权、ID 枚举、过期签名 URL、令牌重放和撤销测试。
6. 模拟数据库暂时不可用、Blob 不可用、模型 429、Workflow 重放和部署切换。
7. 实施备份恢复演练：数据库时间点恢复、Blob 清单、Vault 本地备份。
8. 提供“一键断开并删除云端副本”，生成可核查删除报告。
9. 进行移动端、低带宽、大 Vault 和长笔记性能测试。

### Gate 6：个人正式版

必须通过 [风险与验收矩阵](./07-RISK-TEST-ACCEPTANCE.md) 中全部 P0 安全、可靠性和数据恢复项，才可把 Preview 晋升 Production。

## 10. 阶段 7：受控扩展

扩展按证据顺序，而不是按“功能吸引力”排序：

1. 增量同步、重命名和删除标记；
2. 本地混合检索（关键词、链接、元数据，可选向量）；
3. 指定目标笔记的三方合并；
4. 交付日期感知的复习优先级；
5. FSRS 适配器与工作量模拟；
6. Git/测试/CI/设计成果证据适配器；
7. 能力地图与先修关系；
8. 多设备身份合并；
9. Anki/Obsidian Spaced Repetition 互操作；
10. 多用户和团队能力，只有出现真实需求后才设计。

每一项都必须先写实验假设、成功门槛和移除条件。

## 11. 发布与回退流程

```text
本地契约测试
→ 插件测试 Vault
→ Web Preview
→ 端到端黄金场景
→ 故障与安全测试
→ 数据迁移演练
→ 个人 canary（只开一个项目）
→ Production
→ 24h/7d 复盘
```

回退必须分层：

- Web：Vercel 回滚到上一部署；
- 协议：服务端至少兼容当前和上一个插件协议版本；
- 插件：保留上一稳定 Release，数据迁移必须可向前重放；
- 数据库：迁移使用 expand/contract，先加后删，不在同一发布移除旧字段；
- Workflow：新旧工作流按版本并存，旧运行由旧处理器完成；
- Vault：写入日志保存新建/修改前哈希和备份引用，可由插件撤销。

## 12. 最终完成定义

P0 不是“功能都能点”，而是以下事实同时成立：

- 真实项目任务完成得更快；
- 用户能独立应用，而非依赖 AI 继续完成；
- D7 仍能回忆或迁移关键知识；
- 有价值的经验回到 Obsidian 且没有污染原始知识；
- 用户始终知道哪些数据离开设备，并能删除；
- 任务失败、重试、部署切换和文件冲突不会造成重复或丢失；
- 文档、契约、实现和运行证据保持一致。
