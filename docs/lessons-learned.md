# Vaultide 纠错与经验教训

> 这份文档记录我在维护 Vaultide（OpenMAIC × Obsidian）过程中的真实失败、根因和教训。目的不是追责，而是以后不再犯同样的错。

## 一、真实踩过的坑（按时间顺序）

1. 内容质量差：Vaultide 把 OpenMAIC 的“交互优先”改成了“slide 优先”，课堂像讲义。
2. 生成被反复拦截：来源门、证据门、质量门太多，资料浅就整体拒绝。
3. 数据库打满：Neon 免费 512MB 被知识图谱投影无限累积吃满。
4. 模型密钥失效：Vercel 里的 DeepSeek key 过期，返回 401 → 空响应。
5. “照抄 OpenMAIC”做成反复打补丁，每补一次破一次。
6. 部署没生效：Vercel 未和 GitHub 自动部署关联，一直在测旧代码。
7. 改共享开关引发连锁 bug：关掉 `shouldEnforceCourseQuality` 导致场景内容/动作返回 `quality=undefined`。

## 二、每个坑的根因与教训

### 1. 没先拿确切错误就动手
- 表现：多次“猜”问题，而不是先查数据库/日志。
- 教训：**先查“哪一步、什么错误码、什么原文”，拿不到就不改。**

### 2. 改共享代码前没查清所有依赖
- 典型：`shouldEnforceCourseQuality` 被 6 处引用，我只想到其中几处，没 grep 全。
- 结果：场景内容/动作接口在 `qualityGateEnabled=false` 时提前 `break`，返回 `quality=undefined`，worker 报 `scene_content_response_incomplete`。
- 教训：**改一个函数/开关前，`grep` 出每一个调用点，逐个确认，再改。**

### 3. 部署前没做端到端验证
- 表现：只跑单元测试就部署，没真正跑一次完整生成。
- 教训：**部署前必须做一次真实端到端验证（本地脚本 + 真实模型），确认整条链路走通。**

### 4. 没确认部署真的生效
- 表现：push 到 GitHub 就以为 Vercel 自动部署了，其实没有。
- 教训：**改完先确认“线上跑的是新代码”，再让用户测。**

### 5. 大改动零敲碎打，不一次做完整
- 表现：“照抄 OpenMAIC”拆成 N 个小补丁，每补一次破一次。
- 教训：**方向定了就一次性规划完整、理清依赖、整体验证通过再上。**

### 6. 说得多、问得多，但想得不够
- 表现：反复问“要不要这样做”，又没把每个改动想透。
- 教训：**少问“要不要”，多做“想清楚 + 做完整 + 验证”。**

## 三、硬规矩（以后必须遵守）

1. 先查确切错误，不猜。
2. 改共享代码前，`grep` 所有调用点。
3. 部署前做端到端验证。
4. 部署后确认线上版本。
5. 大改动一次做完整，不留半成品。

## 四、遇到问题时的标准排查流程

1. **定位**：查数据库 `course_planning_runs` / `course_generation_jobs` / `course_generation_steps` 的 `last_error_code` 和 `last_error_detail`，拿到确切错误。
2. **追溯**：根据错误码，`grep` 代码里的抛出点，找到是哪一行、哪个函数。
3. **依赖**：`grep` 这个函数/开关的所有引用，确认改动会影响谁。
4. **最小修复**：只改确切的根因，不顺手改别的。
5. **端到端验证**：跑真实生成（真实模型），确认整条链路走通。
6. **确认部署**：确认线上是新代码，再交付。
